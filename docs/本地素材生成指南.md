# 本地游戏素材生成指南

适用环境：ComfyUI + FLUX.2 klein 4B。目标是让 Rocky 评价美术，由 Codex 组织提示词、调用本地工作流、处理图片并检查游戏规格。首个使用项目是 [Jerry’s Challenge](games/jerrys-challenge/素材生成规格.md)。

本文是部署后的接入约定，**当前没有连接或验证本机 ComfyUI，也没有实现自动生成程序**。文中的任务模板可以直接作为以后实现程序的输入；实际节点参数必须绑定到部署后成功运行的工作流。

## 1. 交付原则

模型负责生成候选画面，处理程序负责格式和尺寸，Rocky 负责判断好不好看、像不像我们要的游戏。提示词不能保证精确像素尺寸、透明背景、角色一致性或正确动画。

因此，“能用于游戏”的保证落实在最终交付检查：不合格的结果留在候选目录，修复或重新生成；只有技术检查通过、且美术经 Rocky 认可的资源才能进入游戏工程。不能把不合格原图简单缩到 32×32 就算完成。

默认使用本地模型，不自动切换到付费云服务。先做推理和参考图编辑，不把训练 LoRA 当作第一步。

## 2. 部署完成后需要交给 Codex 的东西

| 输入 | 内容 |
| --- | --- |
| 服务地址 | 例如 `http://127.0.0.1:8188`；如果运行在另一台机器，提供实际可访问的局域网地址 |
| 环境记录 | ComfyUI 版本、模型完整文件名、精度或量化格式、相关自定义节点及版本 |
| 文生图工作流 | 在你的 ComfyUI 中成功运行过，并导出 **API 格式 JSON** 的工作流 |
| 参考图编辑工作流 | 同样提供成功运行的 API JSON 和一张测试输入、对应输出 |
| 读写位置 | 允许读取的参考图目录、候选输出目录；避免覆盖原始下载素材 |
| 游戏和任务 | 例如 `jerrys-challenge`，新增可爱小狐狸，先出单张待机角色 |

普通界面工作流 JSON 和供 `/prompt` 使用的 API 图不是同一种结构。若版本界面名称不同，以能实际提交并成功出图的导出方式为准。不要求你手工填写节点 ID。

首次接入由 Codex 检查服务、读取节点说明、跑一张小样，确认模型、图片上传、保存输出和读取结果全链路可用，再建立节点映射。服务保持本机或可信局域网可访问即可，无需暴露公网。

模型选择以官方 **FLUX.2-klein-4B 蒸馏版** 为起点；它与 Base 版的采样设置不能混用。分辨率、采样步数、引导、采样器及调度器继承已经验证的官方工作流，调整时逐项记录。不要直接套用其他模型的负面提示词或 CFG 配置。[官方模型说明](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B)、[ComfyUI 官方教程](https://docs.comfy.org/tutorials/flux/flux-2-klein)。

## 3. 每次制作的输入流程

你只需用自然语言说明：

> 给 Jerry’s Challenge 加一个可爱的小狐狸，可供两个玩家选择。橙色毛、奶油色肚子、绿围巾。先看四个造型，保持现在游戏的粗像素风。

Codex 将其整理为任务单，缺失的技术参数读取游戏规格。只有影响创意且无法推断的问题才需要你补充。

1. **明确用途**：角色、道具、地形、背景或 UI；属于哪个游戏。
2. **固定身份**：身体比例、轮廓、配色、服装、朝向、不可改变的特征。
3. **准备参考**：当前游戏截图、已认可角色、允许用于 AI 参考的素材。记录出处和使用条件；免费可下载不等于允许输入 AI。真人家庭照片只在你明确提供并允许时使用。
4. **生成造型候选**：默认四个种子，每张单独保存，附编号。先不生成完整动画。
5. **你选方向**：例如“B 的头和耳朵，围巾改成 D 的颜色”。收敛为一张认可的角色母版。
6. **母版驱动动作**：每次只修改姿势，保持身份、比例、镜头和光照。逐帧生成与审核，再拼接动画。
7. **处理与验收**：透明化、像素整理、统一缩放和锚点、打包、Godot 预览。你看实际大小和动图，不能只看放大原图。

每次反馈保留“认可的内容 / 要修改的内容 / 不能改变的内容”。相同输入、种子和版本用于追溯，但跨硬件、节点或版本不承诺逐像素重现。

## 4. 提示词如何构建

把提示词分为固定风格、角色身份、当前动作、画面约束四段。程序从任务单组合，生成后保存完整文本；不要每帧重新发明角色。

### 固定风格段

```text
Game-ready side-view pixel-art character concept for a warm, playful
cooperative platform adventure for young children. Chunky readable pixel
clusters, simple silhouette, restrained shading, crisp hard edges,
limited coordinated colors, proportions readable at a 32 by 32 pixel
logical sprite size. Match the approved reference's visual simplicity.
```

### 身份段示例

```text
One small friendly fox, oversized rounded head, short compact body,
orange fur, cream muzzle and belly, dark brown feet, a short green scarf,
two pointed ears and one bushy tail with a cream tip. Keep these exact
features and proportions throughout the series. Facing right, strict
side view with the face still clearly readable.
```

### 单张母版的动作与画面段

```text
Neutral standing pose, arms relaxed, both feet supported at the same
ground level. One complete character only, centered, generous clear
margin around ears and tail. Flat solid magenta background for later
background removal; the character contains no magenta. No floor, cast
shadow, text, labels, border, UI, props, scenery, perspective or blur.
```

品红仅是可选抠图底色；若角色本身含品红，换一种不与角色颜色冲突的纯色。底色剔除仍需检查边缘，不能把同色角色区域一并删除。FLUX 输出不能默认有真实透明通道；棋盘格图案不等于透明背景。若采用额外抠图模型，需先核对其许可证及边缘质量。

### 参考编辑：跑步单帧

```text
Use the approved character reference as the identity and style source.
Keep the same fox, silhouette proportions, palette, scarf, face, camera
and light. Change only the pose: running to the right, frame 3 of an
8-frame cycle, passing pose with the left leg moving forward under the
body, right leg moving backward, arms counter-swinging. Keep the body
scale and root position consistent with the other approved frames.
Show the entire character with clear margins on the same flat backdrop.
```

“第 3 帧”本身不能教会模型动画：必须同时提供动作表、认可的母版，必要时提供可合法使用的姿势参考。跑步至少规划接触、下沉、经过、腾空，再交替左右腿；逐帧检查循环连接与脚滑。复杂动作生成失败时，保留母版并人工修帧，比反复要求大图里准确排满几十格更可控。

提示词里的 `32 by 32` 表示目标可读性，实际生成分辨率读取工作流，最终由处理程序产出 32×32。不要指望模型遵守网格、帧数或输出文件名。

### 其他素材的提示词变化

| 用途 | 增加的描述 | 必须额外检查 |
| --- | --- | --- |
| 道具 | 单个物体、侧视、轮廓清晰、留空白边、无投影 | 缩小后可辨认，不与背景混色 |
| 地形 | 指定 16×16 逻辑格、上下左右边缘用途、可连接方向 | 实际拼贴接缝、碰撞面、重复纹理 |
| 背景 | 与角色相同的粗像素密度、低对比远景、明确分层 | 无可误认成平台的细节，无烧进图里的 UI |
| 游戏 UI | 木头、铜件等游戏材质；分别制作边角和中心区域 | 九宫格边距、文字安全区、缩放后的接缝 |

背景分层、无缝平铺和九宫格都需要后处理或手工整理；提示词写出要求不代表已经符合要求。

## 5. 本地调用的实现约定

这部分供后续 Codex 实现调用器，不要求 Rocky 手工操作 API。

1. 读取 `/system_stats` 与 `/object_info`，核对服务及必需节点；加载已验证的 API 工作流副本。
2. 通过工作流绑定表填写提示词、种子和可调整参数。参考图经 `/upload/image` 上传，使用返回的文件标识填入对应输入节点。不能假设编辑模型一定只需要一个 `LoadImage` 节点。
3. 向 `/prompt` 提交 `{"prompt": <API节点图>, "client_id": <本次客户端标识>}`。检查校验错误、`node_errors`，保存返回的 `prompt_id`。
4. 通过 WebSocket 或轮询 `/history/{prompt_id}` 等待。必须区分排队、完成、执行错误和中断；不能把“历史记录存在”直接当作成功。
5. 确认成功状态和指定保存图片节点的输出。按返回的 `filename`、`subfolder`、`type` 请求 `/view`，保存到本次任务目录，校验图片可解码。预览消息不能替代最终保存图片。
6. 保存任务单、工作流快照、参数、种子、模型版本、原图和结果清单。执行错误不允许产生 `ready` 标记。

节点绑定表记录“用途 → 节点 ID → input 字段”，覆盖文本、种子、参考图和保存节点；ID 从实际 JSON 发现，不能编造固定号码。工作流或节点版本变化后先重新试跑。

默认每轮四张、串行排队。超时写入任务状态，先检查原任务再决定重试，避免重复排队。每个失败任务最多自动重试一次；模型缺失、显存不足、节点错误应直接报告。不要调用全局 `/interrupt` 去取消其他人的任务。

API 依据：[官方服务路由](https://docs.comfy.org/development/comfyui-server/comms_routes)、[官方执行消息](https://docs.comfy.org/development/comfyui-server/comms_messages)。认证、访问权限及超时按实际部署配置，不在文档或任务记录中保存密钥。

## 6. 文件组织与处理

建议生成工作区放在已忽略的 `.asset-review/local-generation/`，按游戏和任务隔离：

```text
.asset-review/local-generation/jerrys-challenge/fox-v001/
  job.json                 # 任务单与状态
  workflow-api.json        # 本次实际执行图
  manifest.json            # 参数、来源、种子、输出校验与审批记录
  raw/                     # 不修改的模型原图
  candidates/              # 带编号的预览
  approved/                # Rocky 认可的母版及帧
  processed/               # 处理后的游戏文件
  reports/                 # 技术报告、原尺寸预览、动画预览
```

后处理顺序：解码 → 去背景 → 检查透明边缘 → 统一像素化与配色 → 全角色统一裁切范围和缩放 → 按根锚点放置逐帧 → 拼接条带 → 验收 → 游戏内预览。

所有动作共用角色比例和坐标基准，禁止逐帧单独“放大到填满”。最近邻缩放可避免平滑，但不能自动消除模型原图的噪点和不规则像素块；必要时人工整理轮廓。跳跃的身体位移按动作表保留，不能把每一帧的脚都强行贴到底部。

去除散点需要保留尾巴、围巾、独立配件或特效。现有 [Tom/Jerry 导入脚本](../games/jerrys-challenge/tests/import_character_sheet.gd) 专用于两个角色的 8×4 源图，并只保留每格最大连通区域，**不可作为通用导入器直接批量运行**，也会覆盖既定角色路径。新流程应输出暂存文件，审阅后才替换资源。

## 7. 最终验收门槛

| 检查 | 通过要求 | 谁负责 |
| --- | --- | --- |
| 文件 | PNG 可解码，最终角色为 RGBA8，命名和尺寸与任务规格一致 | 自动检查 |
| 透明 | 实际 alpha 存在；角色像素风默认只含 0/255；有透明边距，无假棋盘底 | 自动检查 + 边缘预览 |
| 内容边界 | 每帧非空，角色无越界；边缘触碰报错或明确人工豁免 | 自动检查 |
| 帧结构 | 帧数、顺序、尺寸、文件完整；没有缺帧或额外网格线 | 自动检查 + 人工看图 |
| 对齐 | 共用缩放和根锚点，脚底和运动轨迹符合动作设计 | 数值检查 + 动画预览 |
| 风格和动作 | 可爱、像同一角色、无肢体错误、循环自然、与现有场景统一 | Rocky 评价，Codex 整理修改 |
| 游戏导入 | Godot 成功加载，最近邻显示；选人、左右移动、跳落均正常 | Codex 在游戏中验证 |

自动检查无法证明“姿势正确”或“没有脚滑”，需要预览。透明区域应清理隐藏 RGB，避免后续处理出现色边；检查纯色底残留、半透明光晕和误删区域。尺寸检查使用解码后的像素尺寸，不能根据文件名判断。

`ready` 必须同时包含技术检查通过和 Rocky 的美术认可记录。原始图及生成记录保留供回退；向正式工程复制时明确文件清单，不静默覆盖现有角色。新增角色还需更新选人登记，单独放入 PNG 不会自动出现在菜单里。

## 8. 第一轮建议

先用一个原创小动物验证闭环：四张母版候选 → 选一张 → 制作 4 帧待机 → 看原尺寸与循环 → 完成跑跳落 → 放进游戏。先把一个角色真正做成可用资产，再扩展家庭成员、道具和场景。

部署后可直接对 Codex 说：

> 按《本地素材生成指南》接入这个 ComfyUI 地址和两个 API 工作流。先检查连接和输入输出，不改现有角色；给 Jerry’s Challenge 做四个小狐狸造型候选，我选好以后再做动画。

这样每次需要你决定的是美术方向；提示词构建、任务记录、格式处理、规格检查与游戏接入由 Codex 继续完成。
